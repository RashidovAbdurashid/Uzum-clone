# Uzum Market Clone — Фазы 1–5

Каркас проекта на Next.js 15 / TypeScript / Tailwind 4: аутентификация, каталог/поиск/товар,
полный флоу оформления заказа, и теперь — рабочая админ-панель и кабинет продавца с реальными
мутациями (модерация товаров, статусы заказов, роли пользователей, категории, отзывы, баннеры).

**Текущий режим: без базы данных.** Вместо PostgreSQL/Prisma/Redis используются in-memory
mock-хранилища — сайт запускается командой `npm install && npm run dev` без Docker.

## Быстрый старт

```bash
npm install
cp .env.example .env
openssl rand -base64 32   # результат вставьте в .env как AUTH_SECRET
npm run dev
```

Откройте http://localhost:3000.

### Тестовые аккаунты

- **Супер-админ**: `admin@uzum-clone.local` / `ChangeMe123!` → доступ в `/admin`
- **Продавец**: `seller@uzum-clone.local` / `ChangeMe123!` → доступ в `/seller/dashboard`
- **Покупатель**: любой номер вида `+998901234567` на `/login` (телефон+OTP) или через
  `/register` (телефон+OTP → имя/email/пароль). Код печатается в терминал dev-сервера,
  не отправляется по SMS.
- На `/login` теперь есть переключатель «Телефон / Email» — форма email+пароль полностью рабочая
  (управляемые поля, `signIn("credentials", ...)`).
- В `/account/settings` можно сменить пароль (или установить его впервые, если аккаунт создан
  только через телефон+OTP и пароля ещё нет) — управляемая форма с `value`/`onChange` на всех
  полях пароля.

## Что реализовано в Фазах 4–5 (админка и кабинет продавца)

- **Модерация товаров** (`/admin/products`, `/seller/products`): статус PUBLISHED/PENDING/
  REJECTED/ARCHIVED влияет на видимость в публичном каталоге — не PUBLISHED-товары не
  показываются на витрине
- **Управление заказами** (`/admin/orders`, `/seller/orders`): смена статуса по всей цепочке
  PENDING → ... → COMPLETED/CANCELLED/RETURNED, статус сразу виден покупателю в `/account/orders`
- **Пользователи** (`/admin/users`, `/admin/sellers`): смена роли и блокировка/разблокировка
- **Категории** (`/admin/categories`): добавление/удаление (2 уровня, как в каталоге), сразу
  отражается в мега-меню и на витрине
- **Модерация отзывов** (`/admin/reviews`, чтение — `/seller/reviews`): approve/reject
- **Баннеры** (`/admin/banners`): добавление/удаление, сразу видно на главной странице
- **Финансы и аналитика** (`/admin/finance`, `/admin/analytics`, `/seller/finance`,
  `/seller/analytics`): реальные расчёты (оборот, комиссия 15%, выплата) из фактических
  тестовых заказов + график продаж (Recharts) за 14 дней
- **Пункты выдачи** (`/admin/pickup-points`): только просмотр
- Честные заглушки (не выдуманы как «готово», явно помечены): `/admin/promotions`,
  `/admin/pages` — CRUD не реализован, есть только описание что планируется

Все мутации идут через Server Actions (`src/actions/admin.ts`) с проверкой роли **на сервере**
(не только через middleware) — `src/lib/admin-store.ts` держит состояние в памяти поверх
статичных моков каталога.

## Демо-упрощения (важно понимать при тестировании)

- **Нет привязки товара к продавцу**: у `Product` в моках есть `brandSlug`, но нет `sellerId` —
  любой SELLER-аккаунт видит и модерирует весь каталог целиком, а не только «свои» товары.
  В реальной схеме (см. историю — раздел 4 исходного ТЗ) это поле есть в модели `Product`.
- Заявок на модерацию продавцов нет — тестовый продавец засеян сразу как ACTIVE.
- Финансовые расчёты (комиссия 15%, выплаты) — упрощённая формула без реальных транзакций/выплат.

## Что реализовано в Фазе 3 (оформление заказа)

- **Checkout** (`/checkout`, требует входа): доставка (ПВЗ по городу / курьер с адресом) →
  оплата (наличные, Click, Payme, Uzum Bank, рассрочка — без реальных платёжных интеграций) →
  подтверждение
- **Заказы**: `createOrderAction` создаёт заказ (`UZM-2026-XXXXX`), очищает корзину, редиректит
  на страницу заказа с таймлайном статусов
- **Пункты выдачи** (`/pickup-points`): список по городам, без интерактивной карты

## Что реализовано в Фазе 2 (каталог)

- Каталог с фильтрами/сортировкой, мега-меню категорий, страница товара с вариантами и отзывами,
  поиск, корзина и избранное (Zustand + localStorage), 20 товаров / 12 категорий / 3 баннера

## Исправленный баг стилей (важно, если форкаете этот код)

Изначально все компоненты использовали классы вида `bg-[--color-brand]` — это компилируется в
**невалидный CSS** (`background-color: --color-brand`, без `var()`), поэтому фирменный цвет
нигде не применялся и сайт выглядел чёрно-белым. Исправлено: цвета зарегистрированы через
`@theme` в `globals.css`, что заставляет Tailwind v4 генерировать рабочие классы `bg-brand`,
`text-brand`, `border-brand`, `bg-brand-dark`, `bg-badge-*` и т.д. Если добавляете новый цвет —
регистрируйте его в `@theme`, а не через `bg-[--your-var]`.

## Как вернуть настоящую базу данных

`src/lib/mock-db.ts` (пользователи), `src/lib/orders-store.ts` (заказы), `src/lib/admin-store.ts`
(мутации админки) и `src/lib/queries.ts` + `src/lib/mock-data/*` (каталог) написаны с
async-сигнатурами, имитирующими будущие DB-запросы — замена на Prisma/другую ORM должна менять
только тела функций, не их вызовы в компонентах.

## Технические примечания

- **Логгер (Pino)**: транспорт `pino-pretty` через worker-thread ломается под бандлером
  Next.js — путь до воркер-файла не резолвится. В `src/lib/logger.ts` используется обычный
  `pino()` без транспорта.
- **Изображения**: SVG-плейсхолдеры отрисовываются через обычный `<img>`, а не `next/image`.
